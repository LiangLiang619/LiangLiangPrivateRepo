## 一、C/C++ 基础

### 1. C 和 C++ 的核心区别

**一句话答案**：C 是面向过程的语言，C++ 是在 C 基础上发展出的支持面向对象、泛型编程的多范式语言，同时提供了更强的类型安全和更丰富的标准库。

**展开**：

| 维度 | C | C++ |
| --- | --- | --- |
| 编程范式 | 面向过程 | 面向过程 + 面向对象 + 泛型 + 部分函数式 |
| 封装 | 无（只能用 struct + 函数） | class / 访问控制 (public/protected/private) |
| 多态 | 无（函数指针模拟） | 虚函数、动态绑定 |
| 泛型 | 无（宏 / void\*） | 模板 (template) |
| 内存管理 | malloc/free | new/delete（会调用构造/析构），智能指针 |
| 类型检查 | 弱，隐式转换多 | 更严格，支持 `static_cast` 等四种显式转换 |
| 函数特性 | 无重载、无默认参数 | 函数重载、默认参数、引用传参 |
| 标准库 | 标准 C 库 | STL（容器、算法、迭代器）、RAII |
| 异常 | 无（错误码） | try/catch 异常机制 |

**面试加分点**：
- C++ **兼容大部分 C**，但不是完全超集（例如 C++ 中 `void*` 不能隐式转其他指针，函数必须声明原型）。
- C++ 引入 **RAII**（资源获取即初始化），把资源生命周期绑定到对象生命周期，是 C++ 内存/资源管理的核心思想。
- 游戏开发中：引擎底层（如 UE 的容器 `TArray`/`TMap`）大量利用模板与 RAII，而不是裸 C。

**面试话术**：
> C 和 C++ 最本质的区别在于编程范式。C 是纯面向过程的语言，程序就是一个个函数按流程组织起来的；而 C++ 在兼容 C 的基础上引入了面向对象和泛型编程，提供了类和封装、继承、多态，还有模板、STL、异常处理这些机制。另外 C++ 的类型检查更严格，内存管理也从 malloc/free 升级到了 new/delete 和智能指针，并且引入了 RAII 这个核心思想，把资源的生命周期和对象绑定在一起。在实际的游戏开发里，比如虚幻引擎，底层容器 TArray、TMap 就大量用到了模板和 RAII。所以说 C++ 能在保留 C 高性能的同时，写出更安全、更易维护的大型工程代码。

### 2. 面向过程和面向对象的区别

**一句话答案**：面向过程 (POP) 以"函数/步骤"为中心，把问题拆成一步步的过程依次调用；面向对象 (OOP) 以"对象"为中心，把数据和操作数据的方法封装成对象，通过对象间协作解决问题。

**核心思想对比**：

| 维度 | 面向过程 (Procedure-Oriented) | 面向对象 (Object-Oriented) |
| --- | --- | --- |
| 关注点 | **怎么做**：分析解决步骤，用函数实现 | **谁来做**：抽象出对象，由对象承担职责 |
| 基本单元 | 函数 + 数据（数据与函数分离） | 类 / 对象（数据与方法绑定） |
| 组织方式 | 自顶向下、流程化 | 封装、继承、多态 |
| 数据与操作 | 数据是全局/参数，函数操作数据 | 数据被封装在对象内，通过方法访问 |
| 复用方式 | 函数复用 | 继承、组合、多态复用 |
| 扩展性 | 需求变化时改动大，牵一发动全身 | 易扩展、易维护，符合开闭原则 |
| 耦合度 | 较高 | 较低（封装隐藏细节） |
| 性能 | 略高（无虚函数/对象开销） | 略低（有虚表、对象构造等开销） |
| 典型语言 | C、Pascal | C++、Java、C# |

**举例说明（洗衣服）**：
- **面向过程**：把过程拆成 `放衣服() → 加水() → 洗涤() → 脱水()` 一串函数，按顺序调用。
- **面向对象**：抽象出"洗衣机"对象，它拥有 `洗()` 方法，内部封装了上述所有步骤，使用者只需 `洗衣机.洗()`。

**优缺点**：
- 面向过程：**优点**是流程清晰、性能高、适合简单/线性任务；**缺点**是数据和逻辑分离，代码复用和维护困难，规模大时难以管理。
- 面向对象：**优点**是封装、继承、多态带来高复用、易维护、易扩展，适合复杂系统建模；**缺点**是抽象设计有门槛，有一定运行时开销。

**面试加分点**：
- 两者不是对立而是互补——OOP 的方法内部通常还是面向过程的实现；实际项目常混用。
- C 是纯面向过程，C++ 兼容面向过程同时支持面向对象；能否用好取决于对问题域的抽象。
- 游戏开发中：UE 的 Actor / Component / GameMode 体系是典型 OOP（继承 + 多态）；但性能热点（如大量实体的批处理）近年更倾向 **数据导向设计 (DOD) / ECS**，用面向数据的思路提升缓存命中，避免 OOP 的虚调用和内存分散开销。可主动提及这一趋势，体现对性能的理解。

**面试话术**：
> 面向过程和面向对象的核心差别在于思考问题的出发点。面向过程关注的是"怎么做"，把一件事拆成一步步的过程，用函数依次实现，数据和操作是分离的；面向对象关注的是"谁来做"，先抽象出对象，把数据和操作数据的方法封装在一起，让对象各自承担职责，再通过对象之间的协作完成任务。打个比方，洗衣服用面向过程就是放衣服、加水、洗涤、脱水一串函数顺序调用；用面向对象就是抽象出一个洗衣机对象，它内部封装好这些步骤，我只要调用它的"洗"方法就行。面向对象靠封装、继承、多态带来更好的复用性和可维护性，更适合复杂系统建模。当然两者不是对立的，实际项目往往混用，面向对象方法的内部实现其实还是面向过程的。在游戏开发里，虚幻的 Actor、Component 体系是典型的面向对象，但对性能热点，比如大量实体的批处理，现在更倾向于用数据导向设计或者 ECS，通过面向数据的方式提升缓存命中、避开虚调用开销。

### 3. const 关键字的用法和修饰区别

**一句话答案**：`const` 表示"只读约束"，编译期保证被修饰对象不被修改；根据位置不同，可修饰变量、指针、引用、成员函数、返回值等。

**主要用法**：

```cpp
const int a = 10;             // 常量，编译期不可改

// 指针相关（关键：看 const 在 * 左边还是右边）
const int* p;                 // 指向常量的指针：*p 不可改，p 可改（指向可变）
int* const p2 = &x;           // 常量指针：p2 不可改，*p2 可改
const int* const p3 = &x;     // 都不可改

// 引用
void func(const string& s);   // 常量引用传参：避免拷贝 + 防止修改（最常用）

// 成员函数
class A {
    int m_val;
public:
    int get() const;          // const 成员函数：不能修改成员变量，const 对象只能调 const 方法
};

// 返回值
const int& getRef() const;    // 返回常量引用，防止外部通过返回值修改内部
```

**记忆技巧（从右往左读）**：`const` 修饰它左边的东西；若左边没有，则修饰右边。

**面试加分点**：
- `const` 成员函数本质是把 `this` 从 `A* const` 变成 `const A* const`。
- `mutable` 可以让成员变量在 const 成员函数中仍能被修改（如缓存、计数器）。
- `const` 与 `#define` 区别：`const` 有类型、有作用域、编译期检查、可调试；宏是纯文本替换。优先用 `const`/`constexpr`。
- `constexpr`（C++11）：编译期常量表达式，比 `const` 更强，能用于数组大小、模板参数等。

**面试话术**：
> const 表示一种只读约束，编译期就能保证被它修饰的东西不被修改。它的用法很多：修饰普通变量就是常量；修饰指针要特别注意 const 的位置，在星号左边是指向常量的指针、内容不能改，在星号右边是常量指针、指向不能改；最常用的是修饰函数参数，用 const 引用传参，既能避免大对象拷贝又能防止被修改；还能修饰成员函数，表示这个函数不会修改成员变量，const 对象也就只能调用 const 成员函数。判断 const 到底修饰谁有个技巧，就是从右往左读，它修饰左边的东西。跟宏比起来，const 有类型、有作用域、能做编译期检查、也方便调试，所以现在更推荐用 const 和 constexpr 来代替 #define。

### 4. static 关键字有几种用法

**一句话答案**：`static` 有三大类用法——修饰局部变量（延长生命周期）、修饰全局变量/函数（限制文件作用域）、修饰类成员（属于类而非对象）。

**四种场景**：

1. **局部静态变量**：生命周期延长到程序结束，但作用域仍在函数内；只初始化一次。
   ```cpp
   void f() { static int count = 0; count++; }  // 多次调用 count 累加
   ```
   常用于**单例模式**（C++11 起局部静态变量初始化是线程安全的，Meyers Singleton）。

2. **全局静态变量 / 静态函数**：作用域限制在当前 **编译单元（.cpp 文件）**，其他文件不可见，避免命名冲突（内部链接）。

3. **静态成员变量**：属于类本身，所有对象共享一份，需在类外定义（分配存储）。
   ```cpp
   class A { static int s_count; };
   int A::s_count = 0;   // 类外定义
   ```

4. **静态成员函数**：不依赖对象，没有 `this` 指针，只能访问静态成员，可通过 `类名::函数` 调用。

**面试加分点**：
- 静态变量存储在**全局/静态存储区（.data / .bss）**，不在栈也不在堆。
- 未显式初始化的静态变量默认零初始化（.bss 段）。
- C++17 的 `inline static` 成员变量可在类内直接初始化。

**面试话术**：
> static 主要有三大类用法。第一种是修饰局部变量，它会把变量的生命周期延长到整个程序结束，但作用域还在函数内，而且只初始化一次，常用来做单例，C++11 之后局部静态变量的初始化还是线程安全的。第二种是修饰全局变量或者函数，把它们的作用域限制在当前这个 cpp 文件里，其他文件看不到，可以避免命名冲突。第三种是修饰类成员，静态成员变量属于类本身、所有对象共享一份，需要在类外定义；静态成员函数没有 this 指针，只能访问静态成员，可以直接用类名去调用。补充一点，静态变量是存放在全局静态区的，不在栈也不在堆上，没显式初始化的会被零初始化。

### 5. 指针和引用的区别，什么场景用引用

**一句话答案**：指针是一个存放地址的变量，可以为空、可以重新指向；引用是变量的别名，必须初始化、不能为空、不能改绑，本质上更安全。

**对比表**：

| 维度 | 指针 | 引用 |
| --- | --- | --- |
| 是否可为空 | 可以是 `nullptr` | 不能为空（必须绑定有效对象） |
| 是否必须初始化 | 否 | 是 |
| 是否可改绑 | 可以指向别的对象 | 一旦绑定不可更改 |
| 是否占内存 | 是（存地址，通常 8 字节） | 概念上是别名（底层常用指针实现，但语义上不独立占空间） |
| 多级 | 支持多级指针 `int**` | 无多级引用 |
| 自增含义 | `p++` 移动指针 | `r++` 操作被引用的对象 |
| sizeof | 指针大小 | 被引用对象的大小 |

**引用底层到底是什么**：

引用在 **语言语义层面** 是"别名"——它不是一个独立的对象，没有自己的地址，对引用的所有操作都会直接作用到被绑定的对象上。但在 **编译器实现层面**，引用绝大多数情况下就是一个**常量指针（`T* const`，即指向不可变的指针）**，只是编译器帮你自动做了"解引用"，让你在语法上感觉不到指针的存在。

```cpp
int a = 10;
int& r = a;      // 语义：r 是 a 的别名
r = 20;          // 语义：改的是 a

// 编译器底层大致等价于：
int* const pr = &a;   // 用一个不可改指向的指针存 a 的地址
*pr = 20;             // 每次用 r 都自动解引用
```

关键点：
- **是否占内存"看情况"**：作为函数参数、成员变量时，引用底层通常占用一个指针大小的空间（要存被绑定对象的地址）；但对于**局部引用**（如 `int& r = a;`），编译器往往能直接优化成"a 的另一个名字"，**不占任何额外空间**，汇编里根本看不到 r。所以标准并没有规定引用一定占空间，这是"未指定"的实现细节。
- **`sizeof(r)` 返回的是被引用对象的大小**（如 `sizeof(int)`），而不是指针大小——这印证了语言层面把它当作对象本身，而不是指针。
- **没有"空引用"**：因为引用必须在定义时绑定一个已存在的对象，编译器不会给它 nullptr 的机会（除非你写了 `*(T*)nullptr` 这种未定义行为）。
- **不能改绑**：因为底层是 `T* const`，指向被固定死了，`r = b` 不是让 r 指向 b，而是把 b 的值赋给 r 绑定的那个对象。

> 一句话总结：**引用 = 编译器帮你自动解引用的常量指针 + 语言层面的"别名"语义**。它把指针的能力（间接访问）保留下来，同时用编译期约束（必须初始化、不能为空、不能改绑）换来了更高的安全性和更简洁的语法。

**引用的典型应用场景**：

1. **函数传参避免拷贝（最常见）**：传大对象时用 `const T&` 只读传入，既省掉一次深拷贝、又保证不被修改；需要在函数内修改实参时用 `T&`。
   ```cpp
   void Process(const FLargeStruct& data);   // 只读，零拷贝
   void Modify(FVector& outPos);             // 直接改调用方的对象（输出参数）
   ```

2. **函数返回引用以支持链式调用 / 避免拷贝**：运算符重载常用。
   ```cpp
   MyClass& operator=(const MyClass& rhs);   // 返回 *this，支持 a = b = c
   std::ostream& operator<<(std::ostream& os, const T& v);
   ```

3. **范围 for 循环中原地遍历/修改**：`for (auto& item : container)` 用引用避免拷贝并能就地修改；只读遍历用 `const auto&`。

4. **给复杂表达式起别名，提升可读性**：`auto& comp = actor->components[i];` 之后直接用 `comp` 操作。

5. **移动语义中的右值引用 `T&&`**：这是引用的另一大类，用于实现移动构造和完美转发（详见第 20 题）。

**面试加分点**：
- 引用底层通常由指针实现，但语言层面是别名，局部引用编译器往往能优化掉、不占空间。
- 函数**切勿返回局部变量的引用**（函数结束后局部对象销毁，形成悬空引用，UB）。
- `const T&` 可以绑定到**临时对象（右值）**，并把临时对象的生命周期延长到该引用的作用域结束——这是 `const T&` 传参能接受字面量/临时值的原因。
- 引用一旦绑定就固定，所以类里有引用成员时**必须在初始化列表中初始化**，且这样的类默认不能拷贝赋值（因为引用不能改绑）。

**面试话术**：
> 指针和引用最大的区别是：指针本身是一个存地址的变量，它可以为空、可以不初始化，也可以随时改指向别的对象；而引用是某个变量的别名，必须在定义时就初始化，不能为空、也不能再改绑，所以天生更安全。要说引用底层到底是什么，其实在语言语义上它是别名，没有独立的身份，你对它的操作都会直接作用到被绑定的对象上；但在编译器实现层面，它绝大多数情况就是一个常量指针，也就是指向被固定死的指针，编译器帮你自动做了解引用，所以你用起来感觉不到指针的存在。正因为底层是常量指针，它才不能为空、不能改绑。它占不占空间要看情况，作为函数参数或成员变量时通常会占一个指针大小来存地址，但局部引用编译器一般能直接优化成同一个变量的别名，不占额外空间；而且 sizeof 一个引用返回的是被引用对象的大小，而不是指针大小。至于应用场景，最常见的就是函数传参，用 const 引用传大对象既避免拷贝又防止修改，需要修改实参时用非 const 引用做输出参数；还有运算符重载返回引用支持链式调用，范围 for 循环用引用原地遍历和修改，以及右值引用去支持移动语义。需要注意的是，函数千万不要返回局部变量的引用，否则会产生悬空引用。

---

### 6. 什么时候用指针，什么时候用引用

**使用指针的场景**：
- 变量可能**不指向任何对象**（可选参数），需要 `nullptr` 表达"空"。
- 需要在运行时**改变指向**（遍历数组、动态内存管理、链表/树等数据结构）。
- 需要动态分配、所有权转移（此时优先用智能指针）。

**使用引用的场景**：
- 参数始终引用有效对象、不允许为空，用引用让代码更简洁。
- 传递大对象避免不必要拷贝（`const T&`），或希望直接修改传入对象。

**一般建议**：
- **默认用引用**：更直观、更安全，不需要判空。
- **用指针处理"可能无对象"或"需要重新绑定"的情况**。
- 现代 C++：需要所有权语义时用**智能指针**，仅观察不拥有时用裸指针或引用。

**面试话术**：
> 我一般的原则是默认优先用引用，因为它更直观也更安全，不需要额外判空。只有几种情况才用指针：一是这个变量可能不指向任何对象，需要用 nullptr 来表达"空"这种可选语义；二是需要在运行时改变指向，比如遍历数组、操作链表和树这类数据结构；三是需要动态分配内存或者转移所有权。而且在现代 C++ 里，如果涉及所有权，我会优先用智能指针，只是观察、不拥有对象的时候才用裸指针或者引用。

## 二、内存管理

### 7. C++ 内存分区有哪些

**一句话答案**：一个 C++ 程序运行时的内存主要分为五个区——栈区、堆区、全局/静态区、常量区、代码区。

| 分区 | 存储内容 | 管理方式 |
| --- | --- | --- |
| **栈区 (stack)** | 局部变量、函数参数、返回地址 | 编译器自动分配释放，后进先出 |
| **堆区 (heap)** | `new`/`malloc` 动态分配的内存 | 程序员手动申请/释放（或智能指针） |
| **全局/静态区 (.data/.bss)** | 全局变量、静态变量 | 程序启动分配，结束释放；.data 存已初始化，.bss 存未初始化(零) |
| **常量区 (.rodata)** | 字符串字面量、const 常量 | 只读，程序结束释放 |
| **代码区 (.text)** | 编译后的机器指令 | 只读，防止意外修改 |

**面试加分点**：
- 栈从高地址向低地址增长，堆从低地址向高地址增长。
- 栈空间有限（一般几 MB），递归过深或大数组放栈上会**栈溢出 (stack overflow)**。
- `char* s = "hello";` 中 `"hello"` 在常量区，试图修改是未定义行为。

**面试话术**：
> 一个 C++ 程序运行时的内存大致分成五个区。栈区存放局部变量、函数参数和返回地址，由编译器自动分配和释放；堆区是 new 或 malloc 动态申请的内存，需要程序员自己管理或者交给智能指针；全局静态区存放全局变量和静态变量，其中已初始化的在 data 段，未初始化的在 bss 段；常量区存放字符串字面量和常量，是只读的；最后是代码区，存放编译后的机器指令，也是只读的。要注意栈是从高地址往低地址增长，空间有限一般就几 MB，所以递归太深或者在栈上放大数组会导致栈溢出。

---

### 8. 堆和栈的区别，什么情况下会内存泄漏

**堆 vs 栈**：

| 维度 | 栈 | 堆 |
| --- | --- | --- |
| 管理方式 | 编译器自动 | 手动 new/delete（或智能指针） |
| 分配效率 | 高（移动栈指针） | 低（需查找空闲块，可能系统调用） |
| 空间大小 | 小（几 MB，有上限） | 大（受限于可用内存） |
| 生长方向 | 高→低地址 | 低→高地址 |
| 碎片 | 无 | 会产生内存碎片 |
| 生命周期 | 作用域结束自动释放 | 手动释放，否则一直存在 |

**内存泄漏的常见情形**：
1. `new`/`malloc` 后忘记 `delete`/`free`。
2. 指针被重新赋值前未释放原有内存（丢失了指向堆内存的唯一指针）。
3. 异常导致 `delete` 被跳过（RAII / 智能指针可解决）。
4. 容器中存放裸指针，清空容器时未释放指向的对象。
5. `new[]` 却用 `delete`（不匹配，未定义行为）。
6. **循环引用**：两个 `shared_ptr` 互相持有，引用计数永不归零。

**如何避免**：
- 优先用**智能指针**（`unique_ptr`/`shared_ptr`）和 **RAII**。
- 循环引用用 `weak_ptr` 打破。
- 工具：Valgrind、AddressSanitizer (ASan)、UE 的 MallocLeakDetection。

**面试话术**：
> 堆和栈的区别主要体现在管理方式、效率和大小上。栈是编译器自动管理的，分配就是移动一下栈指针，效率很高，但空间小、有上限，作用域结束就自动回收；堆是手动 new/delete 管理的，分配要去找空闲块、可能触发系统调用，效率相对低，但空间大，而且会产生内存碎片，用完不释放就会一直占着。内存泄漏最常见的就是 new 之后忘了 delete，或者指针重新赋值前没释放原来的内存、异常导致 delete 被跳过，还有两个 shared_ptr 互相持有形成循环引用。避免的办法主要就是用 RAII 和智能指针，让资源随对象自动释放，循环引用用 weak_ptr 打破，平时还可以借助 ASan、Valgrind 这类工具来检测。

### 9. new 和 malloc 的区别，底层原理

**一句话答案**：`malloc/free` 是 C 库函数，只负责分配/释放原始内存；`new/delete` 是 C++ 运算符，除了分配内存还会调用构造/析构函数。

**对比表**：

| 维度 | malloc | new |
| --- | --- | --- |
| 本质 | 库函数 | 运算符（operator） |
| 是否调用构造/析构 | 否 | 是（new 调构造，delete 调析构） |
| 返回类型 | `void*`，需强转 | 具体类型指针，无需强转 |
| 参数 | 需手动传字节数 | 编译器根据类型自动计算大小 |
| 失败返回 | 返回 `NULL` | 抛出 `std::bad_alloc` 异常（除非 `nothrow`） |
| 是否可重载 | 否 | 可重载 `operator new`/`operator delete` |
| 内存来源 | 堆 | 自由存储区（通常也是堆） |

**底层原理**：
- `new T` 分两步：① 调用 `operator new(sizeof(T))` 申请原始内存（底层通常调 `malloc`）；② 在这块内存上调用 T 的构造函数。
- `delete p` 分两步：① 调用 p 的析构函数；② 调用 `operator delete(p)` 释放内存（底层通常调 `free`）。
- `malloc` 底层：小块内存从内存池/空闲链表分配（如 ptmalloc、tcmalloc），大块内存可能直接向 OS 申请（`brk`/`mmap`）。分配的内存前会有一小段元数据记录块大小，供 `free` 使用。

**面试加分点**：
- `new`/`delete` 与 `new[]`/`delete[]` 必须配对；数组版本会额外存储元素个数以便逐个析构。
- **定位 new (placement new)**：在已分配的内存上构造对象，UE 的容器、内存池大量使用。
- new 失败可用 `new(std::nothrow) T` 返回 nullptr 而非抛异常。

**面试话术**：
> malloc 和 new 最本质的区别是：malloc 是 C 的库函数，只负责分配一块原始内存，返回 void 指针需要自己强转，还得手动算字节数；而 new 是 C++ 的运算符，它不仅分配内存，还会自动调用构造函数来初始化对象，返回的就是具体类型的指针。对应地，delete 会先调析构函数再释放内存，而 free 只是释放内存。从底层看，new 其实分两步，先调 operator new 申请内存，这一步底层通常就是调 malloc，然后在这块内存上调用构造函数。另外 new 分配失败会抛 bad_alloc 异常，malloc 失败是返回 NULL，而且 new 和 delete、new[] 和 delete[] 必须配对使用。在引擎里还常用到 placement new，也就是在已经分配好的内存上直接构造对象，内存池和容器实现里用得很多。

### 10. new 的时候是怎么计算类型空间大小的

**一句话答案**：编译期通过 `sizeof(T)` 确定单个对象大小（考虑成员大小 + 内存对齐填充 + 虚表指针），数组则为 `n * sizeof(T)` 并可能附加长度信息。

**详细过程**：

1. **编译期计算对象大小**：
   - `sizeof(T)` 由编译器根据 T 的内存布局算出。
   - 内置类型直接返回固定大小（如 `sizeof(int)` 通常 4）。
   - 类/结构体：所有非静态成员大小之和 + **内存对齐填充 (padding)**；若含虚函数，还会加上一个**虚表指针 (vptr)**（32 位 4 字节 / 64 位 8 字节）。

2. **内存对齐与填充**：
   - 为提高访问效率，编译器按成员对齐要求在成员间插入填充字节。
   - 结构体总大小是最大对齐要求的整数倍。
   ```cpp
   struct A { char c; int i; };   // sizeof 通常为 8（c 后填充 3 字节）
   ```

3. **new 的两步过程**：
   - `new T` → 调 `operator new(sizeof(T))`；`new T[n]` → 调 `operator new[](n * sizeof(T) [+ 额外记录长度的空间])`。
   - 拿到内存后调用构造函数完成初始化。

4. **operator new 的实现**：接收大小参数，底层调 `malloc` 或 OS API 申请连续内存；可重载实现定制分配策略，但传入的大小仍由 `sizeof` 计算而来。

**面试加分点**：可用 `alignof(T)` 查询对齐要求，`alignas` 指定对齐；结构体成员顺序影响大小（把大成员放前面能减少填充）。

**面试话术**：
> new 一个对象时，它需要的空间大小是编译期通过 sizeof 算出来的。对于内置类型直接返回固定大小；对于类或者结构体，会把所有非静态成员的大小加起来，再加上因为内存对齐产生的填充字节，如果这个类还有虚函数，还要再加一个虚表指针的大小。内存对齐是为了让 CPU 访问更高效，编译器会在成员之间插入填充，让每个成员都落在合适的地址上，整个结构体的大小也会是最大对齐要求的整数倍。所以 new T 的时候传给 operator new 的就是 sizeof(T)，new T[n] 就是 n 乘以 sizeof(T)，数组还会额外记录元素个数以便析构。有个小技巧，把大的成员放在前面能减少填充，让结构体更紧凑。

### 11. C++ 智能指针有哪些，分别有什么特点

**一句话答案**：C++11 提供 `unique_ptr`（独占所有权）、`shared_ptr`（共享所有权 + 引用计数）、`weak_ptr`（弱引用，打破循环引用）；`auto_ptr` 已废弃。

| 智能指针 | 所有权 | 特点 | 使用场景 |
| --- | --- | --- | --- |
| `unique_ptr` | 独占 | 不可拷贝，只能 `move` 转移；零额外开销 | 明确单一所有者，默认首选 |
| `shared_ptr` | 共享 | 引用计数，计数归零才释放；有控制块开销 | 多个对象共享同一资源 |
| `weak_ptr` | 不拥有 | 不增加计数，需 `lock()` 提升为 shared_ptr | 打破 shared_ptr 循环引用、观察者 |
| `auto_ptr`(废弃) | 独占 | 拷贝时转移所有权，语义危险，C++17 移除 | 不要用 |

**核心机制**：
- **RAII**：智能指针在析构时自动释放资源，避免手动 delete 遗漏。
- `shared_ptr` 内部有**控制块**，记录强引用计数 (use_count) 和弱引用计数；计数操作是**原子的**（线程安全的是计数，指向的对象本身不保证）。
- **循环引用问题**：两个 `shared_ptr` 互指导致计数永不为 0 → 内存泄漏，用 `weak_ptr` 解决。

**面试加分点**：
- 优先用 `make_unique` / `make_shared`（异常安全 + `make_shared` 一次分配对象和控制块，减少一次内存分配）。
- `unique_ptr` 可自定义删除器（管理文件句柄、UE 资源等）。
- UE 有自己的智能指针体系：`TSharedPtr`/`TSharedRef`/`TWeakPtr`（普通 C++ 对象）、`TUniquePtr`，以及针对 UObject 的 `TObjectPtr`/`TWeakObjectPtr`（配合 GC）。面试 UE 岗位可主动提及。

**面试话术**：
> C++11 提供了三种智能指针。unique_ptr 是独占所有权的，不能拷贝只能 move 转移，几乎没有额外开销，是我默认的首选；shared_ptr 是共享所有权的，内部用引用计数，多个指针共享同一个对象，计数归零才释放，但它有一个控制块的开销，而且计数操作是原子的；weak_ptr 是弱引用，不增加计数，主要用来打破 shared_ptr 的循环引用，用的时候通过 lock 提升成 shared_ptr。它们的核心都是 RAII，析构时自动释放资源，避免手动 delete 遗漏。实践中我会优先用 make_unique 和 make_shared，既异常安全，make_shared 还能把对象和控制块一次性分配、少一次内存分配。虚幻引擎其实也有自己的一套，比如管理普通 C++ 对象的 TSharedPtr、TWeakPtr，还有针对 UObject、配合垃圾回收的 TWeakObjectPtr。

## 三、面向对象与多态

### 12. 面向对象的三大特性

**一句话答案**：封装、继承、多态。

1. **封装 (Encapsulation)**：把数据和操作数据的方法绑定在一起，通过访问控制（public/protected/private）隐藏内部实现细节，只暴露必要接口。降低耦合，提高安全性。

2. **继承 (Inheritance)**：子类复用父类的属性和方法，并可扩展或修改，形成 "is-a" 关系。支持代码复用和层次化建模。

3. **多态 (Polymorphism)**：同一接口在不同对象上表现出不同行为。分为编译期多态（函数重载、模板）和运行期多态（虚函数）。

**面试加分点**：有时会加上"抽象 (Abstraction)"作为第四特性。游戏开发中，UE 的 Actor/Component 体系就是继承 + 多态的典型应用（如 `Tick`、`BeginPlay` 的虚函数重写）。

**面试话术**：
> 面向对象有三大特性：封装、继承、多态。封装是把数据和操作数据的方法绑在一起，通过 public、private 这些访问控制隐藏内部实现，只暴露必要的接口，好处是降低耦合、提高安全性；继承是子类复用父类的属性和方法，还能扩展或修改，形成 is-a 的关系，实现代码复用和层次化建模；多态是同一个接口在不同对象上表现出不同的行为，分编译期的重载、模板，和运行期的虚函数。在虚幻里这三点体现得很明显，比如 Actor、Component 的继承体系，还有 BeginPlay、Tick 这些虚函数的重写，就是继承加多态的典型应用。

---

### 13. 什么是多态，多态的实现原理

**一句话答案**：多态是"同一接口、不同实现"，即通过基类指针/引用调用虚函数时，实际执行的是对象真实类型的函数。运行期多态通过**虚函数表 (vtable) + 虚表指针 (vptr)** 实现动态绑定。

**分类**：
- **静态多态（编译期）**：函数重载、运算符重载、模板。编译期确定调用哪个函数。
- **动态多态（运行期）**：虚函数。运行期根据对象实际类型确定调用。

**实现原理（动态多态）**：
1. 类中声明 `virtual` 函数后，编译器为该类生成一张**虚函数表 (vtable)**，存放虚函数地址。
2. 每个对象内部有一个**虚表指针 (vptr)**，指向所属类的 vtable。
3. 通过基类指针调用虚函数时，程序先通过 vptr 找到 vtable，再从表中取出对应函数地址调用 → **动态绑定**。

```cpp
class Base { public: virtual void speak() { cout << "Base"; } };
class Dog : public Base { public: void speak() override { cout << "Dog"; } };

Base* p = new Dog();
p->speak();   // 输出 Dog（运行期通过 vptr 找到 Dog 的 vtable）
```

**多态生效的三个条件**：① 有继承；② 子类**重写 (override)** 父类虚函数；③ 通过**基类指针或引用**调用。

**面试话术**：
> 多态简单说就是"同一接口、不同实现"，通过基类的指针或引用去调用虚函数时，实际执行的是对象真实类型的那个函数。它分两种，静态多态是编译期确定的，比如函数重载和模板；动态多态是运行期确定的，靠虚函数实现。动态多态的原理是：一个类只要有虚函数，编译器就会给它生成一张虚函数表，里面存着虚函数的地址，每个对象里有一个虚表指针指向这张表；调用虚函数时，程序先通过对象的虚表指针找到虚函数表，再从表里取出对应函数的地址去调用，这就是动态绑定。多态生效有三个条件：要有继承、子类要重写父类的虚函数、并且要通过基类的指针或引用来调用。

### 14. 虚函数表是怎么工作的

**一句话答案**：编译器为每个含虚函数的类生成一张虚函数表 (vtable)，表中存放该类各虚函数的地址；每个对象含一个 vptr 指向自己类的 vtable，调用虚函数时通过 vptr → vtable → 函数地址完成动态绑定。

**工作细节**：
- **vtable 是类级别的**（每个类一张，所有对象共享），**vptr 是对象级别的**（每个对象一个，通常放在对象内存布局最前面）。
- 构造对象时，构造函数会设置 vptr 指向当前类的 vtable。
- **继承时**：子类继承父类 vtable 的布局；若子类重写某虚函数，则表中对应槽位替换为子类的函数地址；子类新增的虚函数追加到表末尾。
- 调用 `p->func()`：
  1. 通过 `p` 找到对象；
  2. 取对象开头的 vptr；
  3. 在 vtable 中按固定偏移找到 func 的地址；
  4. 调用。

**面试加分点**：
- 虚函数调用比普通调用多一次**内存间接寻址**，且**难以内联**，有性能开销（但通常很小）。
- 多重继承时对象可能有**多个 vptr**（每个基类一个）。
- **构造函数中调用虚函数不会多态**：因为此时 vptr 还指向当前正在构造的类（子类部分尚未构造）。
- 纯虚函数 (`virtual void f() = 0;`) 在 vtable 中对应槽位通常指向一个报错桩，含纯虚函数的类是抽象类，不能实例化。

**面试话术**：
> 虚函数表是编译器为每个含有虚函数的类生成的一张表，里面按顺序存放这个类各个虚函数的地址。要区分两个概念：虚函数表是类级别的，一个类一张、所有对象共享；虚表指针是对象级别的，每个对象里都有一个，通常放在对象内存布局的最前面。对象构造的时候，构造函数会把虚表指针设置成指向当前类的虚表。发生继承时，子类会继承父类虚表的布局，如果重写了某个虚函数，表里对应的槽位就会被替换成子类的函数地址，子类新增的虚函数则追加到表的末尾。所以调用一个虚函数，实际是先通过对象拿到虚表指针，再按固定偏移在表里找到函数地址去调用。要注意虚函数调用比普通调用多了一次间接寻址，而且难以内联，会有一点性能开销；还有在构造函数里调用虚函数是不会有多态效果的，因为那时虚表指针还指向当前正在构造的类。

### 15. 为什么析构函数一般要写成虚函数

**一句话答案**：当用**基类指针指向子类对象并 delete** 时，如果基类析构函数不是虚函数，只会调用基类析构函数，子类的析构函数不会被调用，导致子类资源泄漏。

```cpp
class Base { public: ~Base() { } };                 // 非虚
class Derived : public Base {
    int* data;
public:
    Derived() { data = new int[100]; }
    ~Derived() { delete[] data; }
};

Base* p = new Derived();
delete p;   // 只调用 ~Base()，~Derived() 没调用 → data 泄漏！
```

**正确做法**：把基类析构函数声明为 `virtual ~Base() {}`，这样 delete 时会先调用子类析构再调用基类析构（多态析构）。

**面试加分点**：
- 规则：**只要一个类可能被作为基类（有虚函数 / 会被继承并多态使用），就应该把析构函数写成虚函数。**
- 反之，如果类不打算被继承，虚析构会带来 vptr 开销，没必要。
- C++11 可用 `final` 禁止继承，或不写虚析构表明"不作为多态基类"。
- **纯虚析构函数**也合法，但必须提供函数体（用于抽象类但又需要正常析构子类时）。

**面试话术**：
> 析构函数写成虚函数，主要是为了正确释放子类的资源。当我们用一个基类指针指向子类对象，然后 delete 这个指针的时候，如果基类的析构函数不是虚函数，就只会调用基类的析构函数，子类的析构函数不会被调用，这样子类里申请的资源就泄漏了。把基类析构函数声明成 virtual 之后，delete 就会先调用子类析构再调用基类析构，完成完整的析构过程。所以有个经验法则：只要一个类可能被当作基类、会被多态使用，就应该把它的析构函数写成虚函数；反过来，如果这个类不打算被继承，加虚析构反而会带来虚表指针的额外开销，就没必要了。

### 16. 构造函数可以是虚函数吗，虚函数会带来什么开销

**构造函数不能是虚函数**，原因：
- 虚函数依赖 **vptr**，而 vptr 是在**构造函数执行时才被初始化**的。如果构造函数是虚函数，调用它时 vptr 还不存在，形成"鸡生蛋"矛盾。
- 从语义上，创建对象必须明确知道要创建的**具体类型**，多态是"已有对象、不知具体类型"时才需要，与构造相悖。

**相关补充**：
- 析构函数**可以且常常应该**是虚函数（见上一题）。
- 想实现"根据参数创建不同子类对象"的多态创建，用**工厂模式**或"虚构造/克隆"惯用法（提供 `virtual Base* clone()`）。

**虚函数的开销**：
1. **空间开销**：每个含虚函数的类多一张 vtable；每个对象多一个 vptr（4/8 字节）。
2. **时间开销**：虚调用多一次间接寻址（通过 vptr 查表）。
3. **无法内联**：编译期不知道具体调用哪个函数，难以内联优化，可能影响 CPU 流水线/缓存。
4. **构造/析构开销**：构造和析构时需要设置 vptr。

**面试加分点**：在游戏这种性能敏感场景，**热点路径（如每帧调用的逻辑）应谨慎使用虚函数**；对性能极致要求时可用 CRTP（静态多态/模板）、数据驱动、ECS 等方式规避虚调用开销。

**面试话术**：
> 构造函数不能是虚函数。因为虚函数是要依赖虚表指针来找的，而虚表指针恰恰是在构造函数执行的过程中才被初始化的，如果构造函数本身是虚函数，那调用它的时候虚表指针还不存在，就矛盾了。从语义上讲，创建对象必须明确知道要创建的具体类型，而多态是"已经有对象、但不知道具体类型"时才用的，跟构造正好相反。如果确实想根据参数创建不同的子类对象，一般用工厂模式，或者用 clone 这种虚函数来实现。至于虚函数的开销，主要有几方面：空间上每个类多一张虚表、每个对象多一个虚表指针；时间上每次调用多一次间接寻址；而且编译期不知道具体调哪个函数，难以内联，可能影响流水线和缓存。所以在游戏里每帧都跑的热点路径，我会谨慎使用虚函数，必要时用 CRTP 或者 ECS 这种方式来规避。

### 17. 重载、重写、重定义的区别

| 概念 | 英文 | 发生位置 | 条件 | 绑定 |
| --- | --- | --- | --- | --- |
| **重载** | Overload | 同一作用域 | 函数名相同，**参数列表不同**（个数/类型/顺序） | 编译期 |
| **重写/覆盖** | Override | 父类与子类 | 函数名、参数、返回值相同，父类为 **virtual** | 运行期（多态） |
| **重定义/隐藏** | Redefine/Hide | 父类与子类 | 子类定义同名函数（**参数可同可不同**），父类**非 virtual** 或签名不同 | 编译期 |

**要点**：
- **重载**：与返回值无关（仅返回值不同不能构成重载）。
- **重写**：必须是虚函数，构成运行期多态；建议加 `override` 关键字让编译器检查。
- **重定义（隐藏）**：子类的同名函数会**隐藏**父类所有同名函数（即使参数不同），除非用 `using Base::func;` 引入。

```cpp
class Base {
public:
    virtual void f(int);   // 
    void g(int);
};
class Derived : public Base {
public:
    void f(int) override;  // 重写（Override）
    void g(double);        // 重定义/隐藏（Hide）—— 会隐藏 Base::g(int)
    void f(int, int);      // 也是隐藏（参数不同）
};
```

**面试话术**：
> 这三个概念很容易混。重载是发生在同一个作用域里，函数名相同但参数列表不同，注意跟返回值无关，它是在编译期确定的。重写也叫覆盖，是发生在父类和子类之间，函数名、参数、返回值都相同，而且父类那个函数必须是虚函数，它构成运行期多态，建议加上 override 关键字让编译器帮忙检查。重定义也叫隐藏，也是父类子类之间，子类定义了同名函数，但父类的不是虚函数或者签名不一样，这时候子类的同名函数会把父类所有的同名函数都隐藏掉，哪怕参数不同也一样，除非用 using 把父类的引进来。

---

### 18. 虚继承解决了什么问题

**一句话答案**：虚继承主要解决**菱形继承（钻石继承）中的数据冗余和二义性问题**——确保共同基类在最终派生类中只有一份实例。

```cpp
class Animal { public: int age; };
class Dog : virtual public Animal {};   // 虚继承
class Cat : virtual public Animal {};   // 虚继承
class Pet : public Dog, public Cat {};

Pet p;
p.age = 3;   // OK，只有一份 Animal（若不用虚继承则二义，需 p.Dog::age）
```

**原理**：虚继承时，共同基类的子对象被"共享"。编译器通过**虚基类指针 (vbptr) / 虚基类表**记录虚基类子对象的偏移，运行期定位唯一的虚基类实例。

**代价**：虚继承会增加对象大小（多了 vbptr）和访问成本（需通过偏移间接访问虚基类成员），布局更复杂。

**面试话术**：
> 虚继承主要是用来解决菱形继承带来的问题，也就是当一个类通过两条路径继承了同一个基类时，会导致这个基类的数据出现两份，产生数据冗余和访问上的二义性。用了虚继承之后，编译器会保证这个共同基类在最终的派生类里只有一份实例。它的实现是通过一个虚基类指针或者虚基类表，记录虚基类子对象的偏移，运行期再去定位那唯一的一份实例。代价就是对象会变大、访问虚基类成员要多一次间接，布局也更复杂一些。

---

### 19. 菱形继承是什么，怎么解决

**菱形继承（钻石问题）**：一个类通过两条继承路径继承同一个基类，导致基类成员在最终派生类中出现**两份拷贝**，产生数据冗余和访问二义性。

```
      Animal
      /    \
    Dog    Cat
      \    /
       Pet          // Pet 中含有两份 Animal
```

**产生的问题**：
1. **数据冗余**：`Pet` 中有 `Dog::Animal` 和 `Cat::Animal` 两份 `age`。
2. **二义性**：`pet.age` 编译器不知道用哪一份，报错。

**解决方法**：
- **虚继承**：让 `Dog` 和 `Cat` 虚继承 `Animal`（`virtual public Animal`），使 `Pet` 中只保留一份 `Animal`（见上一题）。
- 或**显式指定路径**（不彻底）：`pet.Dog::age`，但仍有两份数据，只是解决了访问二义性。

**面试加分点**：C++ 支持多重继承所以有菱形问题；Java/C# 用"单继承 + 接口"从语言层面规避了这个问题。实践中应尽量用组合代替复杂继承。

**面试话术**：
> 菱形继承，也叫钻石继承，指的是一个类通过两条继承路径继承了同一个基类。比如宠物类同时继承自狗和猫，而狗和猫又都继承自动物，这样宠物里就有了两份动物的数据。它带来两个问题，一个是数据冗余，有两份重复的成员，另一个是访问二义性，比如访问年龄这个成员时编译器不知道该用哪一份，会报错。解决办法就是让狗和猫虚继承动物，这样宠物里就只保留一份动物的实例了。这其实是 C++ 支持多重继承才有的问题，像 Java、C# 用单继承加接口就从语言层面规避了它，所以实践中我也会尽量用组合来代替复杂的继承。

## 四、现代 C++

### 20. 左值、右值、将亡值，右值引用的作用

**基本概念（C++11 值类别）**：

- **左值 (lvalue)**：有名字、有持久内存地址、可取地址、可出现在赋值号左边。如变量 `a`、`*p`、数组元素。
- **右值 (rvalue)**：临时的、即将销毁、不能取地址的值。分为：
  - **纯右值 (prvalue)**：字面量 `42`、表达式结果 `a+b`、临时对象、函数返回的非引用值。
  - **将亡值 (xvalue)**：expiring value，"即将被移动"的值，通常由 `std::move(x)` 产生，或返回右值引用的函数结果。它既有身份又可被移动。

> 记忆：**左值有身份、不可移动；纯右值可移动、无身份；将亡值有身份、可移动**。

**右值引用 (`T&&`)**：绑定到右值的引用，C++11 引入，核心作用是支持**移动语义**和**完美转发**。

**作用与意义**：

1. **移动语义 (Move Semantics)**：避免不必要的深拷贝。对于临时对象，直接"窃取"其内部资源（如指针、堆内存），而不是拷贝一份。
   ```cpp
   class Buffer {
       int* data; size_t size;
   public:
       // 移动构造：接管 other 的资源，避免拷贝
       Buffer(Buffer&& other) noexcept
           : data(other.data), size(other.size) {
           other.data = nullptr; other.size = 0;  // 置空原对象
       }
   };
   std::vector<Buffer> v;
   v.push_back(Buffer(...));   // 用移动而非拷贝，效率大幅提升
   ```

2. **完美转发 (Perfect Forwarding)**：模板中用 `T&&`（转发引用/万能引用）+ `std::forward<T>` 保持参数的值类别，转发给下层函数。

3. **`std::move`**：本质是把左值**强制转换成右值引用**（`static_cast<T&&>`），它自身不移动任何东西，只是"允许"后续的移动操作发生。

**面试加分点**：
- 移动构造/移动赋值应标记 `noexcept`，否则 `std::vector` 扩容时为保证异常安全会退回用拷贝。
- 移动语义对含大量堆资源的对象（如 `string`、`vector`、UE 的 `TArray`）收益最大。
- 被 `std::move` 后的对象处于"有效但未指定"状态，不应再使用其值（除非重新赋值）。

**面试话术**：
> 左值就是有名字、有持久地址、可以取地址、能放在赋值号左边的东西，比如一个变量；右值是临时的、马上要销毁、不能取地址的值，比如字面量、表达式的结果、返回的临时对象。C++11 还细分出一个将亡值，就是即将被移动的值，通常是 std::move 产生的，它既有身份又能被移动。右值引用就是能绑定到右值的引用，用两个 & 表示，它最大的作用是支持移动语义和完美转发。移动语义的意义在于避免不必要的深拷贝，对于一个临时对象，我可以直接把它内部的资源，比如堆内存指针，"偷"过来，而不是重新拷贝一份，这对 string、vector 这种管理大量堆资源的对象性能提升非常明显。需要提一句，std::move 本身并不移动任何东西，它只是把左值强制转成右值引用，允许后面的移动操作发生；另外移动构造最好标记成 noexcept，否则 vector 扩容时为了异常安全会退回去用拷贝。

## 五、并发与多线程

### 21. 进程和线程的区别

**一句话答案**：进程是操作系统**资源分配**的基本单位，线程是 CPU **调度执行**的基本单位；一个进程可包含多个线程，线程共享进程的地址空间。

**对比表**：

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 定义 | 资源分配的基本单位 | CPU 调度的基本单位 |
| 地址空间 | 独立 | 共享所属进程的地址空间 |
| 通信 | 需 IPC（管道、共享内存等） | 直接读写共享内存/全局变量 |
| 切换开销 | 大（需切换页表、地址空间、刷新 TLB） | 小（同一地址空间，只切换寄存器和栈） |
| 崩溃影响 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能拖垮整个进程 |
| 创建开销 | 大 | 小 |

**为什么线程切换比进程切换快**：
- 同一进程内的线程**共享地址空间（页表、内存映射）**，切换时**无需切换页表、无需刷新 TLB / CPU 缓存**，只需保存/恢复少量寄存器和栈指针。
- 进程切换要切换整个虚拟地址空间，导致 TLB 失效、缓存冷启动，代价高。

**线程共享 / 不共享的资源**：
- **共享**：代码段、数据段（全局/静态变量）、堆内存、打开的文件描述符、信号处理设置、进程 ID。
- **不共享（每个线程独有）**：栈、寄存器（含程序计数器 PC）、线程 ID、线程本地存储 (TLS)、错误码 `errno`、调度优先级。

**面试话术**：
> 进程是操作系统资源分配的基本单位，线程是 CPU 调度的基本单位，一个进程里可以有多个线程，它们共享进程的地址空间。线程切换之所以比进程切换快，是因为同一个进程里的线程共享地址空间，也就是共享页表和内存映射，切换的时候不需要切换页表、不需要刷新 TLB 和缓存，只要保存恢复少量寄存器和栈指针就行；而进程切换要换整个虚拟地址空间，会导致 TLB 失效、缓存冷启动，代价就大得多。线程之间共享的资源包括代码段、全局和静态数据、堆内存、打开的文件描述符这些；不共享的是每个线程各自独有的，比如栈、寄存器、程序计数器、线程 ID 和线程本地存储。

### 22. 有没有做过多线程开发，多个线程访问同一资源如何处理

**核心问题**：多个线程同时读写共享资源会产生**数据竞争 (data race)**，导致结果不确定甚至崩溃。需要**同步机制**保证访问的**互斥性**和**可见性**。

**常见处理方式**：

1. **互斥锁 (mutex)**：保证同一时刻只有一个线程进入临界区。C++ 推荐用 RAII 包装 `std::lock_guard` / `std::unique_lock` 自动加解锁，避免忘记释放或异常导致死锁。
   ```cpp
   std::mutex mtx;
   void add() { std::lock_guard<std::mutex> lk(mtx); shared_data++; }
   ```

2. **读写锁 (`std::shared_mutex`)**：读多写少场景，允许多个读、独占写。

3. **原子操作 (`std::atomic`)**：对简单类型（计数器、标志位）的无锁操作，比锁更轻量。

4. **条件变量 (`std::condition_variable`)**：线程间等待/通知（如生产者-消费者）。

5. **无锁数据结构 / 消息队列**：通过队列把数据从一个线程传给另一个，避免共享。

6. **减少共享**：能不共享就不共享，用**线程局部存储 (TLS)** 或每线程独立数据，最后汇总。

**要点 / 加分**：
- **死锁四条件**：互斥、持有并等待、不可剥夺、循环等待。避免死锁：**固定加锁顺序**、用 `std::lock` 一次锁多个、`try_lock` 超时。
- 锁粒度：粒度太大影响并发，太小增加开销，需权衡。
- **内存可见性**：多核下需要内存屏障/atomic 保证一个线程的写对另一个线程可见（volatile 在 C++ 中**不能**用于线程同步）。
- **游戏引擎中的实践**：主线程负责游戏逻辑和渲染提交，通常用**任务系统 (Task/Job System)** 把可并行的工作（物理、动画、寻路、资源加载）分发到工作线程；UE 用 `TaskGraph`、`Async`、`FRunnable`、`Async Loading`。UI/UObject 操作一般要回到游戏线程。

**面试话术**：
> 多个线程同时读写同一个资源会产生数据竞争，结果不确定甚至崩溃，所以要用同步机制来保证互斥和可见性。最常用的是互斥锁，保证同一时刻只有一个线程进临界区，在 C++ 里我一般用 lock_guard 或 unique_lock 这种 RAII 的方式自动加解锁，避免忘记释放或者异常导致死锁。如果是读多写少，可以用读写锁，允许多个读、独占写；对计数器、标志位这种简单类型，用 atomic 原子操作比加锁更轻量；线程间的等待通知就用条件变量，比如生产者消费者模型。另外要防死锁，最实用的办法是固定加锁顺序，或者用 std::lock 一次锁多个。其实最好的策略是尽量减少共享，能不共享就不共享。结合我的经验来说，我做资源异步加载时，就是在后台线程执行 IO 和解析，通过线程安全队列把结果投递回主线程，再由主线程统一去创建和绑定引擎对象，避免多线程直接操作 UObject；共享的计数用 atomic，队列用 mutex 加 lock_guard 保护，保证异常安全。

### 23. 多线程和多进程适合什么场景，进程间通信方式

**多线程 vs 多进程适用场景**：

| 场景 | 推荐 | 原因 |
| --- | --- | --- |
| CPU 密集、需大量共享数据 | 多线程 | 共享内存快，切换开销小 |
| 需要高稳定性、隔离性（一个崩溃不影响其他） | 多进程 | 地址空间独立，容错强 |
| IO 密集 | 多线程 / 异步 | 等待 IO 时切换执行其他任务 |
| 需要利用多核且任务耦合低 | 多进程 / 多线程均可 | — |
| 安全隔离（如浏览器每个标签页） | 多进程 | 沙箱隔离 |

**进程间通信 (IPC) 方式**：
1. **管道 (pipe)**：匿名管道（父子进程）、命名管道 (FIFO，无亲缘关系进程)。
2. **消息队列**：内核维护的消息链表，按类型收发。
3. **共享内存 (shared memory)**：多个进程映射同一块物理内存，**最快**的 IPC，但需自己配合信号量做同步。
4. **信号量 (semaphore)**：主要用于同步/互斥，配合共享内存使用。
5. **信号 (signal)**：异步通知（如 `SIGKILL`），信息量小。
6. **套接字 (socket)**：可跨主机通信，最通用（本机可用 Unix domain socket）。

**面试加分点**：共享内存最快是因为**数据不需要在内核和用户空间之间来回拷贝**；管道/消息队列/socket 都需要拷贝。游戏中跨进程常用 socket（客户端-服务器）或共享内存（如与外部工具、DS 通信）。

**面试话术**：
> 选多线程还是多进程，主要看场景。如果是 CPU 密集、又需要大量共享数据，用多线程更合适，因为共享内存快、切换开销小；如果更看重稳定性和隔离性，希望一个模块崩溃不影响其他部分，那就用多进程，因为进程地址空间是独立的、容错更好，像浏览器每个标签页用一个进程就是这个道理。进程间通信的方式主要有：管道，包括匿名管道和命名管道；消息队列；共享内存；信号量，主要用于同步；信号，用于异步通知；还有套接字，它最通用、还能跨主机。其中共享内存是最快的，因为数据不需要在内核和用户空间之间来回拷贝，但它需要自己配合信号量做同步。

## 六、网络

### 24. TCP 和 UDP 的区别，为什么游戏用 UDP

**一句话答案**：TCP 是面向连接、可靠、有序但有延迟开销的协议；UDP 是无连接、不可靠、无序但低延迟、轻量的协议。实时游戏对延迟敏感、能容忍少量丢包，所以常用 UDP。

**对比表**：

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认重传） | 不可靠（可能丢包） |
| 顺序 | 保证有序 | 不保证顺序 |
| 拥塞/流量控制 | 有 | 无 |
| 传输方式 | 字节流 | 数据报（保留消息边界） |
| 首部开销 | 20 字节起 | 8 字节 |
| 速度/延迟 | 较慢，延迟高 | 快，延迟低 |
| 一对多 | 仅一对一 | 支持单播/多播/广播 |

**为什么游戏（尤其实时/竞技类）用 UDP**：
1. **低延迟**：无需握手、无确认重传等待，实时性好。对 FPS/MOBA/动作游戏，延迟比偶尔丢包更致命。
2. **旧数据无价值**：游戏状态每帧更新，丢了的旧位置包重传过来也没用，还不如发新的。TCP 的"队头阻塞"会因为一个丢包卡住后续所有数据，反而更糟。
3. **可控性**：可以在 UDP 之上**自己实现可靠性**——只对关键消息（如技能释放、结算）做确认重传，对可丢弃的状态同步（位置、朝向）用不可靠通道。灵活分级。

**UDP 的缺点及应对**：
- 缺点：不可靠、无序、无拥塞控制、可能丢包/乱序/重复。
- 应对：在应用层实现**可靠 UDP**（序列号、ACK、选择性重传、拥塞控制），业界方案如 **KCP、ENet、RakNet、QUIC**，UE 网络层底层也是基于 UDP 自建可靠传输。

**面试加分点**：
- **回合制、卡牌、聊天、登录、支付**等对可靠性要求高、对延迟不敏感的场景仍用 TCP。
- 现代方案 **QUIC**（基于 UDP）兼顾低延迟与可靠有序，解决了 TCP 队头阻塞。
- UE 中 `bReliable` 标记的 RPC 走可靠通道，属性同步默认走不可靠通道（丢了下次同步补上）。

**面试话术**：
> TCP 和 UDP 最核心的区别是可靠性和延迟的取舍。TCP 是面向连接的，要先三次握手，它保证数据可靠、有序，还有拥塞控制和流量控制，但这些机制带来了额外的延迟开销；UDP 是无连接的，不保证可靠也不保证顺序，但它很轻量、延迟低。实时性强的游戏，比如 FPS、MOBA，一般用 UDP，原因有几点：一是它延迟低、实时性好；二是游戏状态每帧都在更新，丢掉的旧数据就算重传过来也没意义了，还不如直接发新的，而 TCP 的队头阻塞反而会因为一个丢包卡住后面所有数据；三是 UDP 更灵活，我可以在它之上自己实现分级可靠性，只对关键消息比如技能释放、结算做确认重传，位置、朝向这种可丢弃的状态同步就走不可靠通道。当然回合制、卡牌、聊天、登录、支付这些对可靠性要求高、对延迟不敏感的场景还是用 TCP。业界在 UDP 上做可靠传输的方案有 KCP、ENet、QUIC，虚幻的网络层底层也是基于 UDP 自建的可靠传输。

## 附：面试速记清单（Cheat Sheet）

- **指针 vs 引用**：引用不能空/不能改绑/更安全；指针可空可改绑。
- **const**：从右往左读，修饰左边；`const T&` 传参最常用。
- **static**：局部延长生命周期、全局限文件作用域、类成员共享。
- **内存分区**：栈、堆、全局静态区、常量区、代码区。
- **new vs malloc**：new 调构造/析构、返回具体类型、失败抛异常、可重载。
- **智能指针**：unique（独占）、shared（计数）、weak（破循环）。
- **多态**：虚函数 + vptr + vtable，运行期动态绑定，三条件（继承/重写/基类指针引用）。
- **虚析构**：基类指针 delete 子类对象要虚析构，否则子类资源泄漏。
- **构造函数不能虚**：vptr 还没建立。
- **重载/重写/重定义**：同作用域参数不同 / 虚函数覆盖 / 子类隐藏父类同名。
- **菱形继承**：虚继承解决，共享一份基类。
- **右值引用**：移动语义 + 完美转发，避免深拷贝。
- **进程 vs 线程**：进程分配资源、线程调度执行；线程切换快（不换页表/TLB）。
- **多线程同步**：mutex/lock_guard、atomic、condition_variable，防死锁固定锁序。
- **TCP vs UDP**：可靠有序 vs 低延迟轻量；游戏用 UDP + 应用层可靠性（KCP/ENet/QUIC）。
