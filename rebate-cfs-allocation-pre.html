Current Pain Points

目前的痛点：规则、数据和执行动作都太分散

秒杀坑位和活动补贴都不是单点计算，而是需要反复取数、筛选、排序、校验和汇总。一旦依赖人工，很容易在效率和准确性之间反复拉扯。

1

数据量大且表格分散

活动排期、Slots Pool、Raw Data 和卖家报价池分布在不同表里，人工汇总耗时，也容易漏掉最新版本。

2

计算链路长

选品、排坑位、算补贴、控预算都要反复试算，一处规则变化就可能触发整套结果重跑。

3

场景切换慢

不同月份、Cluster、类目趋势、大促或 BAU 场景需要不同口径，人工很难快速切换规则。

4

结果难追溯

最终清单能看到，但当时用了哪些筛选条件、资源是否用满、哪些 Shop 拿到坑位，缺少稳定沉淀。

我们需要的不是更努力地拉表，而是一套更聪明、更高效、口径更稳定的工具。
Solution

解决思路：你定规则，系统负责执行

把选品规则、坑位分配、补贴算法和预算控制拆成模块。使用者通过 Bot 交互提出需求，系统按规则自动运行，并把结果回写到 Sheets。

高效汇总

把多张排期表和坑位池汇总成可查询视图，支持按月份、Cluster、Session 快速查看坑位总览。

场景化分配

支持头部店铺与高潜店铺比例自定义，也能按开学季、趋势品类、大促或 BAU 场景调整资源倾斜。

可追溯结果

每次分配都会输出执行清单与汇总报告，方便查看坑位使用率、Shop 分层、补贴消耗和复盘口径。

技术难点在于数据量大、规则分支多、人工口径复杂。单一 Agent 很难稳定完成全链路，因此系统把“对话理解”和“大规模数据处理”拆开：Smart 负责取数和交互，Google Apps Script 负责确定性计算。

Module 01

秒杀坑位模块：查询资源池，并自动生成排期

模块一覆盖两个动作：先查询指定月份与 Cluster 的坑位数量，再根据智能分配逻辑生成可执行坑位排期表。

功能是什么

使用者通过 Bot 输入月份、Cluster、站点、类目或 Top/Growth 配比，系统自动读取坑位池与 Raw Data，完成选店、选品、配额计算、时段填充和结果汇总。

技术上怎么实现

  • Bot 将自然语言需求转成结构化参数。
  • Smart 按参数读取 Slots Allocation 与 Raw Data。
  • Google Apps Script 执行筛选、去重、排序、配额和写回。
  • 用户也可以在 Sheets 中点击按钮，几十秒内直接运行脚本。
Slot Scenarios

模块一具体实现：把分配规则做成可定制能力

不是只生成一张表，而是让使用者能根据不同运营目标调整资源倾斜。

A

头部 / 高潜店铺

支持自定义 Top Shop 与 Growth Shop 坑位比例。头部店铺保障效率，高潜店铺获得成长流量。

B

趋势品类

可按 L2/L3 类目筛选，为开学季、换季、重点趋势品增加坑位曝光。

C

大促 / BAU

大促侧重覆盖与资源打满，BAU 更关注稳定供给和时段分散，两类策略可切换。

D

资源使用率

自动生成汇总板块，展示每个时段是否 100% 用满、每个 Shop 的分层和拿到的坑位数量。

模块一的价值，是把“怎么分坑位”从个人经验变成可配置、可解释、可复盘的运营机制。
Module 02

活动补贴模块：自动选择商品，并分配 Rebate 预算

模块二把全量商品池和卖家报价池放进同一套规则框架，先确定商品来源，再排序，再计算补贴和预算消耗。

Rebate Logic

模块二具体实现：来源、排序、预算都可配置

补贴分配最重要的是口径清楚。系统把每个关键判断拆成可配置项，保证不同活动可以按不同策略执行。

模块 规则 优化后的表达
选品来源 S1-S4 S1 全量池、S2 报价池、S3 交集、S4 报价优先 支持平台主导、商家报名优先、精挑细选和“报价优先且不足补齐”等不同活动策略。
排序方式 复合指标或单字段降序 复合指标使用销售量占比与销售额占比综合评分，并叠加 Mall 与 FBS 提权；单字段排序用于快速按指定指标决策。
预算控制 实际支出 = 补贴单价 × 补贴件数 系统控制最终总支出。预算不足时压缩或截断，预算未用完时可追加商品或提高现有商品补贴。
规则配置 预算、上限、类目、来源、排序、强制用完预算 全部在 Google Sheets 维护，运营修改参数即可重跑，无需进入代码。

核心公式

实际补贴支出 = 补贴单价 × 补贴件数

预算控制的是最终总支出，不是单一商品的补贴单价。这样才能同时兼顾商品覆盖、库存安全和预算使用效率。

强制用完预算

  • M1：继续向下追加符合规则的商品，扩大补贴覆盖。
  • M2：提高已选商品补贴，但不超过单商品上限。
  • 如果超预算，则自动按规则压缩或停止追加。
Traditional vs System

把 Rebate 和 CFS 分配从“人工经验”变成“可交互、可配置、可追溯”的自动化流程。

Smart 负责让用户按需求交互，Google Apps Script 负责大规模数据处理。使用者也可以直接点击按钮运行脚本，几十秒内得到结果。

维度 传统方式 本系统
规则调整 改公式或改代码，容易影响其他字段 改表格参数，系统按新规则执行
选店 / 选品 人工拉 Excel 排序和筛选 自动选店、选品、补位，支持场景化规则
坑位分配 人工排期，容易冲突或分布不均 自动防重复，按剩余坑位和店铺分布分散填充
预算控制 人工估算，预算使用率不稳定 自动计算总支出，支持强制用完预算
结果输出 手动整理清单和汇总 一键生成执行表、汇总表和规则快照
可追溯性 依赖人工记录，复盘成本高 每次分配都有结果留存，便于查看资源使用率和效果
耗时 单次至少 1-2 小时 通常 5-10 分钟内完成完整分配链路，脚本计算可在几十秒内跑完
